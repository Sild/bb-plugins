# Reviewed agent workflows for BB

Adds a compact **Design · Plan · Implement** button group to an existing thread's input form. Design and Plan start Astra with Extra High (`xhigh`) reasoning. Implement starts GPT-6.1-Sol High in a fresh session. Type additional instructions in the input and click the desired workflow directly. Its child receives the visible text draft alongside the workflow prompt and explicit artifact context, without submitting the draft to the source thread. The sent text is cleared only after a successful start; edits made during launch and drafts from failed launches are preserved. Send pending attachments first so the child can inherit them.

Design produces a detailed Project design plan covering goals, users, all high-level components and interactions, architectural choices, and implementation milestones. Plan produces a Detailed implementation plan with proposed modules/crates, types/traits/signatures, applicable database schemas and migrations, call flows, failure handling, and verifiable milestones. Planning is read-only in the repository. The complete Markdown artifact is persisted as the agent's final response. Instructions and exact model settings live in `workflow.yaml`, validated at plugin load.

Design/Plan from Codex source threads use a native session fork with explicit Astra model/reasoning overrides and a Kanban workflow relationship. Other provider threads transfer the complete paginated timeline, including nested tool rows, for Design/Plan. Review and Implement always start fresh sessions, never forks. Their prompts include the complete current artifact, latest composer instructions for Implement, and explicit source/artifact links for recovering requirements. Design/Plan artifacts must include requirements, corrections, decisions/rationale, non-goals, constraints, checkout/branch/HEAD, relevant paths, evidence, validation commands, acceptance criteria and unresolved questions. Existing attachments and referenced artifacts remain available in the shared environment; questions use the persistent inbox and pause dependent work.

Every completed producer automatically receives an independent read-only review. Claude is selected when the chosen machine reports usable quota in all windows. Exhausted, unavailable, or unknown quota selects Codex Astra High. A Claude failure after quota changes can fall back to Codex. Claude's model settings are preserved and High reasoning is requested. Workflow agents keep their native parent empty and declare workflowParentThreadId in their public plugin metadata. Kanban uses that relationship for hierarchy, active ancestors, automatic acceptance and shared-workspace merge checks. This avoids native completion and ownership notices restarting producers or returning unreviewed artifacts. BB's native sidebar displays these threads separately; fork provenance and source links remain available.

The reviewer reads the original requirements and actual artifact, runs proportionate checks, and returns `REVIEW_STATUS: approved` or `REVIEW_STATUS: changes_requested`. Material findings return to the producer for correction. Each revised artifact is independently reviewed again. After three unsuccessful rounds the root receives an unresolved blocker instead of approved work. A question pause, failed turn, absent Done report, missing artifact, or ambiguous verdict never advances as successful work. A changed producer turn invalidates approval of its earlier revision, including on acceptance retries. Pending pre-upgrade reviews and implementation/fix turns are migrated into the new flow.

Thread titles identify the artifact being produced: `[PLAN] Task`, `[DESIGN] Task`, or `[</>] Task`. Each independent review prefixes its producer's title with `[👁]`, giving `[👁][PLAN] Task`, `[👁][DESIGN] Task`, or `[👁][</>] Task`. Chained actions replace leading workflow markers with their own stage, preserving unrelated title tags. Correction rounds and provider fallbacks retain the producer's title, even when the main thread is renamed. Existing thread titles are preserved.

The root receives the complete artifact and independent review only after approval. Completed reviews are automatically Accepted after feedback delivery. Reviewed Plan and Design children are automatically Accepted after delivery and accepted independent review. Implementation acceptance remains a user action, and the plugin never merges, pushes, or deploys on its own.

All agents share one workspace. Tasks default to the project checkout on its current active branch; worktrees require explicit selection. Validate and commit all task-owned implementation/fix changes before Done, preserving unrelated work. Keep one implementation owner, and avoid concurrent edits in the root while an implementation child is working. Handoffs are persisted in plugin KV; acceptance retries after reload without redelivering an already delivered artifact. In-flight dispatch failures are recorded as failed rather than blindly duplicating turns; inspect `bb plugin logs review-implement` for an interrupted handoff.

The group keeps visible text labels, shared border/background, 28px controls, and keyboard focus indicators. Narrow viewports remove decorative icons while retaining all three labels. At 520px or less the group moves just above the input, preserving space for native model, voice and send controls. Native voice/send controls stay in their usual location. There is no manual Review button.

Validation: `./node_modules/.bin/tsc --noEmit`, `./node_modules/.bin/vitest run`, `bb plugin build`, and a live BB composer check. The plugin is versioned in this collection and can be installed from its local package path.
